It’s manageable but not trivial. Rough scope: small app, React/Next 16, admin console UI. Expect 1–2 days for a solid baseline (EN + 1 extra locale) if we keep strings simple and avoid dynamic content translation.

Recommended approach

Library: next-intl (native app router support) or next-i18next. Both handle routing, SSG/SSR, and ICU-style interpolation. I’d pick next-intl for cleaner app router ergonomics.
Structure:
Add /messages/{locale}.json files (e.g., en, es).
Wrap app in NextIntlClientProvider in layout.tsx.
Create a useT helper to shorten calls (t("users.delete")).
Keys: externalize all user-facing strings in src (app, ui, lib). Priority: nav labels, buttons, table headers, toasts, error texts, empty states, auth flows, audit page.
Dates/numbers: use next-intl formatters or Intl.DateTimeFormat with locale from provider; now that date-fns is installed, use format with locale imports per user locale (e.g., import { es } from "date-fns/locale").
Routing/locales: configure i18n in next.config.js (e.g., locales: ["en", "es"], defaultLocale: "en"). Decide between domain vs. path (/es/...) strategy; paths are simplest.
Backend: primarily passthrough; just ensure API error messages you display are localized on the client, or map known error codes to localized copies.
Authentication/OAuth: ensure redirect paths preserve locale (/es/oauth/callback). Add locale-aware links in the login flows.
Testing: snapshot key pages per locale (users, audit, orgs, projects). Verify RTL if you add Arabic/Hebrew (needs dir="rtl" toggling).

Setup + provider wiring: ~1–2 hours.
Extract strings (UI + toasts + errors): ~4–6 hours.
Date/number localization + audit page formatting: ~1 hour.
Locale-aware routing and QA pass: ~2 hours.
Add third locale: +1–2 hours per locale once keys exist.
